# ADR 0001: Serve Qwen3.8-Flash-Next on 1×B300 with vLLM, official FP8, n-gram table in HBM vs offloaded

- **Status:** Proposed
- **Date:** 2026-10-14, revised 2026-10-22 (the MoE target moved from Kimi K3 on
  8×B300 to Qwen3.8-Flash-Next on 1×B300, because only one GPU is available)
- **Goal:** [docs/goal.md](../goal.md)

## Context

The project predicts and measures decode performance on one B300: first a dense
model, then an MoE model, with speculative decoding on both. With one GPU, the
MoE target must fit in a single GPU's HBM. This ADR fixes the model, serving
stack, precision, memory placement, and measurement protocol so later results
are comparable.

### Models (from each Hugging Face `config.json` and model card)

Qwen3.8-Flash-Next (2026-08-24) is Qwen's newest general-purpose LLM on Hugging
Face, and its official FP8 checkpoint fits on one GPU. The other Qwen3.8 MoE,
Qwen3.8-2.4T-A95B, has 2.45T parameters.

| | Qwen3.8-Flash-Next [1][2] | Qwen3.8-27B [3] |
|---|---|---|
| Parameters | 125B main model, 6B active; plus a 51B n-gram embedding and a 4B MTP module. 180.0B in the safetensors, vision encoder included | ~27B dense |
| Layers | 48: 36 Gated DeltaNet (linear) + 12 Qwen Sparse Attention (QSA: GQA with 2 KV heads, head dim 256; an MQA indexer selects a budget of 512 blocks, i.e. 2,048 tokens) | 64: 48 Gated DeltaNet (linear) + 16 full attention (GQA, 4 KV heads) |
| FFN | 512 routed experts + 1 shared, top-10; expert FFN 640; hidden 2560 | dense, 17408 |
| Other | N-gram embedding: 20M rows of bigrams/trigrams, injected at layer 2. Gated Residual: 4 residual branches. Vision encoder (unused here). | — |
| Checkpoint | Official FP8: routed experts and the n-gram table in FP8 (128×128 blocks, dynamic activation scales); everything else BF16; **185.5 GB (172.8 GiB)**. BF16 is 335 GiB and does not fit [4]. | BF16, plus an official FP8 checkpoint |
| Speculative decoding | One built-in MTP layer, "trained with multi-steps" | One built-in MTP layer |

Both models are **hybrid**: most layers keep a fixed-size recurrent state per
sequence, and a minority keep a KV cache that grows per token. The analytical
model must carry both terms from the start. In Flash-Next, QSA also bounds how
many cached tokens each decode step attends to.

### Hardware (1×B300)

- 288 GB HBM3e, up to 8 TB/s [6]. NVIDIA's HGX page lists 2.1 TB for eight
  GPUs rather than 8×288 GB = 2.3 TB [7], so usable capacity must be
  **measured**.
- Host link: PCIe Gen6 ×16, 256 GB/s bidirectional [6]. GB300 instead reaches
  its Grace CPU over NVLink-C2C at 900 GB/s [6]. This sets the cost of
  offloading anything to host memory.
- Dense tensor throughput per GPU, derived from the per-node HGX figures [7]:
  FP4 ≈ 13.5 PFLOPS, FP8 ≈ 4.5 PFLOPS, BF16 ≈ 2.25 PFLOPS.

### Fit check for Qwen3.8-Flash-Next (estimate, to be replaced by the analytical model)

Bytes per component, summed from the FP8 checkpoint's safetensors headers [2]:

| Component | GB |
|---|---|
| Routed experts (FP8) | 120.8 |
| N-gram embedding table (FP8) | 51.3 |
| Gated DeltaNet, QSA, Gated Residual, shared expert, router (BF16) | 7.3 |
| Token embedding + `lm_head` (BF16) | 2.5 |
| MTP module | 2.7 |
| Vision encoder (BF16) | 0.9 |
| **Total** | **185.5** |

- At `--gpu-memory-utilization 0.90`, ~74 GB is left for KV cache, recurrent
  state, activations, and CUDA graphs if all 288 GB are usable, or ~51 GB if
  only ~262 GB (2.1 TB ÷ 8) are.
- Offloading the n-gram table to host memory frees another ~51 GB of HBM.
- Per sequence, with an FP8 KV cache: ~12.7 KB per token of QSA KV and indexer
  keys, plus ~115 MB of fixed Gated DeltaNet state if it is held in FP32
  (`mamba_ssm_dtype: float32`). At concurrency 256 that is ~67 GB for the
  10k/1.5k shape and ~36 GB for 1k/1k. The long shape at 256 may therefore not
  fit with the table in HBM.
- Decode weight bytes per step: ~8.6 GB of BF16 non-expert weights are read
  every step, and each expert touched adds 4.9 MB per layer. At batch 1 that
  is ~11 GB (~1.4 ms at 8 TB/s). Under uniform routing, batch 64 touches ~72%
  of experts per layer (~95 GB) and batch 256 touches ~99% (~129 GB, ~16 ms).
  Real routing is skewed, so these are bounds to test, not predictions.

### Engine status

vLLM's recipe [4] (updated 2026-10-13) lists GB300, the same GPU on a Grace
host, as verified; it does not list HGX B300. It is tuned on the nightly image
and states that stable vLLM ≥ 0.30.0 also runs the model (the latest stable
release is v0.32.0, 2026-10-18 [5]). Relevant points:

- The FP8 checkpoint fits on one GB300. Single-GPU TP1 "suits evaluation and
  development"; multi-GPU TEP is recommended for serving throughput.
- On Blackwell it sets `--kv-cache-dtype fp8` and
  `--attention-config.indexer_kv_dtype fp8`.
- vLLM **enables n-gram embedding CPU offload by default**
  (`--engram-config '{"cpu_offload":true}'`). This keeps the 51B table in host
  RAM and prefetches rows asynchronously. It is required for DEP and on
  80 GB-class GPUs, and optional on H200-class GPUs and larger.
- MTP uses `--speculative-config '{"method":"mtp","num_speculative_tokens":3}'`,
  benchmarked with SPEED-Bench (`--dataset-name speed_bench`), not random tokens.

### Book grounding (Kiely, *Inference Engineering*, 2026)

- §2.4 (pp. 61–67) frames the work as roofline / arithmetic-intensity analysis.
- §2.2.4 (p. 54): under batched inference "you should expect almost all of the
  model parameters to be active at any given time unless sparsity is achieved
  in large-scale Expert Parallelism." With one GPU there is no expert
  parallelism, so the *unique experts touched per batch* term should approach
  all 512 experts per layer as concurrency grows.
- §5.3.2 (pp. 139–140) ranks memory tiers by bandwidth to the GPU (HBM at TB/s,
  host memory at tens to hundreds of GB/s) and notes faster host links on
  GB200-class systems. The book applies this to KV cache; applying it to the
  n-gram table is our extension.
- §5.2 (p. 129): speculative decoding "only improves TPS/ITL, not TTFT."
  §5.2.1 (p. 131): it is "most useful at low batch sizes where there are spare
  compute cycles." The book does not cover MTP; its closest analogues are
  Medusa and EAGLE (§5.2.2–5.2.3, pp. 132–134).
- §4.5.2 (p. 114): change one variable at a time, and expect speculative
  decoding to work against large batch sizes.

## Decision

1. **Engine: vLLM only.** Pin one Docker image digest per phase. Start from the
   latest stable release, and use a pinned nightly only if a needed fix exists
   only there. Record the image digest, vLLM commit, driver, CUDA, FlashInfer,
   and the model revision (Flash-Next FP8 `236dfdf`) with every run.
2. **Precision: native checkpoints.**
   - Flash-Next: the official FP8 checkpoint as shipped (BF16 does not fit).
   - Dense: BF16 vs the official FP8 checkpoint.
   - KV cache: FP8 by default for Flash-Next, including the indexer cache
     (vLLM's Blackwell setting [4]), with BF16 as one comparison point.
3. **Placement on 1×B300: n-gram table in HBM vs offloaded.**
   - **HBM-resident** (`--engram-config '{"cpu_offload":false}'`): every decode
     byte is an HBM byte, which keeps the analytical model simple. This is the
     main sweep.
   - **Offloaded** (vLLM's default): frees ~51 GB for KV cache and state, at
     the cost of host-to-GPU row prefetches over PCIe. Run the same sweep to
     measure what offloading costs per step and how much concurrency it buys.
   - **Text-only:** `--language-model-only` skips the vision encoder.
   - **Excluded:** tensor, expert, and data parallelism, since there is only
     one GPU.
4. **Calibrate on dense first.** Run Qwen3.8-27B on 1×B300 and keep it short.
   The same analytical model, harness, and profiling workflow carry over to
   Flash-Next unchanged.
5. **Measurement protocol.**
   - **Load:** `vllm bench serve` against the OpenAI-compatible server, with
     fixed input/output lengths (ignore EOS) and concurrency in
     {1, 2, 4, 8, 16, 32, 64, 128, 256}.
   - **Shapes:** ~10k in / 1.5k out (matching Artificial Analysis's default) and
     1k in / 1k out (decode-dominated).
   - **Metrics:**
     - TTFT and TPOT/ITL (p50 and p90).
     - Per-user and aggregate output tok/s.
     - Bandwidth utilization = modeled bytes per decode step ÷ measured step
       time ÷ peak HBM bandwidth.
   - **Cold vs warm:** cold is the first requests after server start; warm is
     after a warm-up pass. Prefix caching is off for the main sweep. Server
     start and weight-load time are recorded as their own measurement.
   - **Repeats:** at least 3 runs per point, reporting the mean and spread. Change
     one variable at a time.
   - **Profiling:** Nsight Systems plus the vLLM torch profiler on one decode
     config per model. Attribute time to GEMMs (expert vs other), attention
     (Gated DeltaNet vs QSA, including the indexer), n-gram lookups and
     host-to-GPU copies, and idle or launch gaps.
6. **Speculative decoding.**
   - **Both models:** the built-in MTP layer.
   - **Flash-Next:** sweep `num_speculative_tokens` over {1, 2, 3}; 3 is vLLM's
     recipe default [4].
   - **Prompts:** use real text (e.g., SPEED-Bench, MT-Bench), not random
     tokens, because acceptance on random tokens is meaningless. Fix
     temperature and top_p, since acceptance depends on them.
   - **Sweep across concurrency.** Gains should shrink as the batch grows
     (§5.2.1). For the MoE this should happen sooner: verifying k+1 tokens per
     sequence routes more tokens per step and touches more experts.
   - **Model term:** expected tokens per step comes from acceptance length;
     step cost is the target verifying k+1 tokens plus the draft cost.
7. **Operations.** Tear VMs down after every session. Keep the 186 GB FP8
   checkpoint on persistent storage close to the GPU so it is not re-downloaded
   each session. Offloaded runs need at least 51 GB of free host RAM plus
   headroom [4].

## Alternatives considered

- **Kimi K3 on 8×B300 (the first draft of this ADR):** its 1.56 TB MXFP4
  checkpoint needs eight GPUs, and only one is available. It would have
  exercised TP vs EP and inter-GPU communication, which are now out of scope.
- **Qwen3.8-2.4T-A95B:** the largest current Qwen model; at 2.45T parameters it
  does not fit on one GPU at any native precision.
- **Qwen3.8-Flash-Next in BF16:** 335 GiB, which does not fit.
- **NVFP4 variants (e.g., `Inferact/Qwen3.8-Flash-Next-NVFP4`, the vLLM recipe's
  default, and `nvidia/Qwen3.8-Flash-Next-NVFP4`):** these leave more headroom
  and run at the FP4 rate, but they change the model under test. Revisit only
  as a stretch comparison.
- **Older Qwen MoE models that fit (Qwen3.6-35B-A3B, Qwen3.5-122B-A10B):** older,
  and without Flash-Next's sparse attention or n-gram embedding.
- **DeepSeek V4.1 Flash (the earliest plan):** the target is now a Qwen model.
- **SGLang:** has a Flash-Next cookbook, but one engine keeps the comparison
  about the model, not the engines. Revisit if vLLM's Flash-Next support
  blocks progress.

## Consequences

- **Good:**
  - One engine, one GPU, and native weights keep the residuals attributable to
    the model and memory placement, not to setup or communication.
  - Dense calibration surfaces methodology errors cheaply, and both models run
    on the same GPU, so phases 1 and 2 can share sessions.
  - One GPU gives the cleanest case of §2.2.4: without expert parallelism,
    the weight bytes per step should rise from ~11 GB toward ~129 GB as
    concurrency touches more experts.
- **Memory is tight:**
  - With ~51–74 GB of headroom and the table in HBM, the long shape at
    concurrency 256 may not fit. The analytical model should predict maximum
    concurrency per config *before* the sweep.
  - MTP adds draft-token KV and may add recurrent-state slots; vLLM's recipe
    advises lowering `num_speculative_tokens` under memory pressure [4].
    Speculative runs need their own capacity check.
- **Not a production deployment:** vLLM recommends multi-GPU TEP for
  throughput [4]. The results describe one GPU, not the best way to serve the
  model.
- **Moving target:** Flash-Next is an "experimental preview" architecture and
  vLLM's recipe was tuned on nightly builds. Pinning digests is mandatory, and
  upgrading mid-phase invalidates comparisons.
- **Cost:** loading 186 GB per session is far cheaper than K3's 1.56 TB, but
  sessions should still be batched and well planned.

## Open questions (resolve in the first Flash-Next session)

1. Usable HBM (`nvidia-smi`): 288 GB, or closer to ~262 GB?
2. Does `cpu_offload: false` work at TP1 on HGX B300? With offload on, what do
   the PCIe row prefetches cost per decode step, and do they overlap compute?
3. MoE GEMM path for the block-FP8 experts on B300: which backend vLLM selects,
   and whether activations are quantized to FP8. This decides whether the
   compute roof is the FP8 rate.
4. Do decode attention bytes stop growing past QSA's 2,048-token budget, and
   what does the indexer's scan over the full context cost at 10k tokens?
5. Maximum concurrency that fits per shape and per config (HBM vs offloaded,
   with and without MTP).
